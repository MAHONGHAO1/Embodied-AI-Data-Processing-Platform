# 上传后数采审核与标注工作台设计

状态：第二版线框图已获用户认可；本文为据此整理的书面设计，等待书面规格审查。业务实现及端到端验收尚未开始。

核对代码基线：`da66e15`。需求从任务「优化布局并说明上传方式」（`01a0c7f5-f658-7ca0-9f8d-3c26c96dcbbd`）接续至当前 QuicStudio 任务。采用用户已选择的 A 方案：左侧 Episode、中间视频、底部时间轴、右侧片段描述。

本设计补充 [代码与规格修复计划](../../CODE_SPEC_REPAIR_PLAN_2026-09-22.md) 和 [外部工具前端收尾规格](2026-09-22-quicstudio-sk-frontend-completion-design.md)。涉及新版工作台的交互与接口扩展，以本文为准；单包一次最终入库审核、冻结成员、一包一数采员等已确认规则继续适用。

## 1. 已确认的产品决定

| 主题 | 决定 |
| --- | --- |
| 数采审核所在阶段 | 数据上传、解析与准入检查之后，建批之前；从截图中的「采集管理 → 数采审核」进入 |
| 数采审核操作 | 按包连续观看原始 Episode，上一条／下一条，标记不合格及原因，最后提交整包结论 |
| 标注名称 | 页面及入口统一叫「标注」，不叫「切分＋标注」，不另设切分任务 |
| 标注交互 | 参考 quicdata 的播放器、片段选取、时间轴和边界调整，每个有效片段填写语言描述 |
| 有效范围 | 只选有效片段；未选中的时间默认无效，不进入该标注版本的下游数据集 |
| 重叠规则 | 同一 Episode 有效片段不得重叠，允许首尾相接，允许中间留空 |
| 结果页面 | 和标注共用视频、Episode 导航及时间轴；直接展示提交的片段和描述 |
| 审核操作 | 去掉重复的「审核」标题和模式标签，保留「通过／退回」；审核员不能直接编辑标注 |
| 锁定 | 提交后查看固定提交版本；通过后固定结果；退回后由原标注员修改并重新提交 |

线框图中的「标注／结果查看」侧栏用于演示两种视图。正式应用从对应队列进入，能力由服务端工作项、用户及状态决定，不提供切换身份或自行开启编辑的开关。

## 3. 上传后的数采审核

### 3.1 入口与页面

「数采审核」列表读取数据包接口，显示上传与处理状态、Episode 数量、任务及数采员。上传中和解析中可以查看进度，但不能提交最终审核；符合现有准入规则的包进入审核。已通过或已驳回的包只能查看固定结论及创建补采包。

点击数据包进入独立全屏页：

- 左侧：包内 Episode，显示待查看、已查看、不合格和系统排除状态，可筛选不合格项。
- 中间：常驻视频播放器、播放控制、上一条／下一条；切换时正确更新 Episode、媒体和播放位置。
- 右侧：当前 Episode 的检查摘要、不合格标记和原因；最终提交区展示整包汇总。
- 数采审核不编辑时间片段；标记对象是完整 Episode。系统排除项展示明确原因，不允许人工勾回以绕过准入门禁。

页面保留「已查看」进度，未逐条点击合格不自动等同不合格。最终确认明确展示有效、不合格、系统排除及尚未查看的数量，用户确认整包结论后调用服务端终审。现有批量通过保留，但必须显示有效与排除汇总并复用后端门禁。

### 3.2 草稿与最终结论

新增数采审核草稿记录，按 workspace/package/reviewer 隔离，保存 `draft_version`、Episode 标记及原因、已查看 ID、最近 Episode、来源清单指纹和更新时间。草稿不改变 accepted/rejected/excluded 准入事实，不增加一次审核历史，也不累计有效时长。

保存需要 `base_version`；冲突返回 409，禁止静默覆盖。刷新或重新进入恢复已成功保存的草稿。保存失败时保持页面编辑内容，明显标为未保存；离开前提示尚未保存的内容。

每条不合格 Episode 必须填写原因。终审请求增加结构化的逐 Episode 原因；与 `rejected_episode_ids` 必须对应，最终审核记录一并保存。整包驳回仍必须有整包原因。现有客户端只传 ID 的历史调用继续按其原契约处理，新工作台强制填写详细原因。

终审在同一包锁下校验当前准入事实、草稿来源指纹和请求，形成一次最终结论；来源变化返回冲突并要求刷新核对，不将旧标记应用到新来源。相同终审请求可幂等重放，改变结论的请求不能重放成功。已被其他人终审的草稿转为不可提交状态。

最终审核后锁定原包，补采沿用同任务下新建关联普通数据包的规则。

## 4. 标注工作台

### 4.1 工作单位和布局

工作项仍按包分配，Episode 列表严格来自 `episode_members_json` 的冻结成员及来源 attempt，不动态展开原包。页面顶部只显示「标注」、任务／数据包、保存状态和必要操作。

播放器保持完整画面比例，不裁切源画面。底部时间轴支持定位、缩放、选范围和拖动边界；保留 quicdata 中适用的局部精调、撤销／重做和快捷键。左侧切换 Episode；右侧显示片段起止时间、时长和语言描述。备注、已有评分或结果字段折叠展示，不额外引入必填业务维度。

点击片段列表或时间轴片段，都定位到同一个片段和起点。时间轴显示选中范围与未选范围，展示有效总时长及未选时长。输入框聚焦时不触发播放、删除或片段快捷键。

### 4.2 时间与数据语义

- 有效区间使用左闭右开 `[start_ns, end_ns)`，满足源范围内、起点小于终点和区间无重叠。相接片段允许后一段起点等于前一段终点。
- 显示可用秒和时分秒；持久化使用源时间轴整数纳秒。浏览器使用明确的序列化适配，避免绝对纳秒值被 JS Number 舍入。视频预览时间通过现有精确映射换算，不把压缩视频时间直接当源时间。
- 映射缺失时可以播放和查看，禁用边界编辑与提交并说明原因，不近似生成时间边界。
- 不继承旧切分的「必须连续覆盖完整 Episode」校验；未选范围不需要生成一串无效片段。
- 草稿允许描述未完成；提交时每个有效片段必须有非空语言描述，并验证所有冻结 Episode 都有明确处理结果。
- 对整条没有有效内容的 Episode，提供明确的「本条无有效片段」及原因；空草稿不能自动表示已处理。该状态保存在平台的 Episode 处理结论中，和 QRDF 标注 payload 分开，不随意新增 QRDF 字段。
- 有效片段仍经过当前 QRDF schema 校验。原始文件保持完整；片段是固定来源上的逻辑范围，不为标注操作立即复制或覆盖视频文件。

### 4.3 自动保存与版本

复用现有保存协调器：编辑后防抖、持续编辑时有最长等待时间、同一工项一次只发送一个保存请求。切换 Episode 保留包内草稿；提交前先排空保存队列并拿到最新版本。

保存请求携带 `base_version` 和 `expected_generation`，服务端锁定工项、验证当前分配人及状态，再增加版本。冲突显示服务器版本已变化并保留本地未保存内容，用户重新载入核对后才能继续提交。重新分配、退回、提交或完成后，旧标签页的迟到请求不能覆盖新状态。

页面状态区分未保存、保存中、已保存和保存失败；只有服务端确认成功才能显示已保存或提交成功。

## 5. 标注结果与通过／退回

进入新审核队列工作项后，页面标题为「标注结果」。沿用 Episode 导航、视频和时间轴；右侧直接展示片段范围、时长、语言描述及提交版本，不展示一组禁用的编辑表单，不重复堆叠「审核工作台／标注审核／审核模式」。

页面允许查看完整源视频和未选区间，便于发现漏选；不能拖动边界、增删片段或编辑描述。只有服务端授权的当前审核人能操作，通过／退回作用于整个包级工作项，而不是只作用于当前显示的 Episode。

通过前展示整包有效片段、无有效片段 Episode 和尚未查看数量。退回必须填写原因，返回原标注员修改，原提交版本保留。查看旧版本时不允许把操作提交到新版本。

新增不可变提交记录，关联 annotation work item、提交 ID、提交人、generation、草稿版本以及逐 Episode 的 annotation revision ID、有效范围或无有效片段结论。审核工作项引用当前提交 ID；通过／退回请求携带预期提交 ID 与 generation。并发重提、改派或重复操作只能成功应用一次，不能误审另一份内容。

资产快照从通过的提交记录取明确修订。现有物化来源记录可用于核对迁移；历史记录缺少可靠对应关系时显示「历史结果无法确定」，不猜测成当前最新修订。旧资产快照保持原样。

## 6. 接口衔接

以下路径为本期拟新增或扩展的契约，统一使用现有 `/api/v1` 前缀及响应封装；目前不能视为已实现。

| 接口 | 用途 |
| --- | --- |
| `GET /annotation-work-items/{id}/workbench` | 包信息、冻结 Episode 摘要、草稿版本、generation、已处理状态和服务端能力 |
| `GET /annotation-work-items/{id}/episodes/{episode_id}/workbench` | 当前 Episode 来源时间轴、授权预览及当前草稿；检查工项冻结成员关系 |
| `PATCH /annotation-work-items/{id}` | 扩展预期版本和 generation，保存按 Episode 组织的草稿及处理结论 |
| `POST /annotation-work-items/{id}/submit` | 校验完整处理结果、预期版本和 generation，原子创建不可变提交记录 |
| `GET /review-work-items/{id}/workbench` | 已提交版本、逐 Episode 修订及只读能力 |
| `GET /review-work-items/{id}/episodes/{episode_id}/workbench` | 固定提交下的媒体、时间范围和描述，不读取后来改变的草稿 |
| `POST /review-work-items/{id}/approve`、`/return` | 扩展预期提交 ID 与 generation，并保持权限及包级状态门禁 |
| `GET /data-packages/{id}/intake-review-draft` | 当前审核人的未提交草稿与当前来源指纹 |
| `PATCH /data-packages/{id}/intake-review-draft` | 带预期版本保存标记、原因与查看进度 |
| `POST /data-packages/{id}/intake-review` | 复用最终审核，扩展逐 Episode 原因及来源校验 |

包级摘要不预签所有媒体；只对当前 Episode 按需获取预览，避免大包一次签发过多 URL。签名过期可针对当前媒体刷新，恢复播放位置，不重置草稿。浏览器预览沿用浏览器可访问的端点策略，与外部工具默认内网 OSS 取数分开。

新增只读接口同时校验 workspace、用户权限、当前分配及成员关系；隐藏跨空间资源，不能仅凭 Episode ID 访问其他工项。结果查看权限不能隐式授予编辑权。客户端传来的能力、修订 ID 和来源地址均不作为授权依据。

版本字段对新工作台必填。旧客户端省略版本的兼容处理必须集中在旧入口适配层并在锁内检查当前状态；新页面不使用该兼容分支。算法批量提交沿用现有幂等键和真实 QRDF payload，复用同一提交记录与结果校验；免审同样固定提交版本，不能绕过范围检查。

## 7. 有效片段如何进入资产与导出

本期不能仅改变 UI：启用标注的批次必须把审核通过的有效范围和描述写入不可变资产／数据集版本快照，下游候选和导出只能消费这些范围。

- 数据包入库有效时长保留上传后审核的口径；标注有效时长按非重叠有效区间求和，页面分别命名，不回写原包入库时长。
- 未启用标注的批次继续沿用现有治理有效成员；本规则不把未配置标注的批次判为全部无效。
- 无有效片段的 Episode 保留处理结论和历史溯源，不产生训练样本。整个包没有有效片段可以完成处理；整个批次为零有效内容时保留完成记录和零值汇总，不创建可构建的空数据集或伪造成功导出。
- 数据集版本固定来源对象、准入 attempt、提交 ID、标注修订、有效范围及描述。导出按格式适配器切取或转换这些范围，遵循 QRDF 现有时间与映射规范。
- 原始来源保留完整文件；训练交付不把灰色未选范围混入样本。切分与标注不复活旧 `episode_publish` 物理发布链。
- 原生 LeRobot 直传 export 为独立链路，本期保持现有行为。

## 8. 代码组织与兼容

从 `app.js` 中提取本期工作台状态控制和视图片段，按以下职责拆分：包级工作台数据适配、Episode 播放与时间映射、片段范围编辑、保存协调、结果只读呈现、数采审核草稿。所有网络请求仍经 `api.js`。

复用 quicdata 的交互逻辑及 Studio 已有 `workbench-save.js`、时间轴组件和快捷键设施；连续全覆盖校验、旧 WorkItem 状态机、旧领取/租约或物理发布职责不直接复制到新流程。只改本期经过的模块，不趁机做全仓重构。

新队列提供真实工作台入口；移除直接空提交和未查看内容就一键假通过的入口。生产环境不得将 demo、弹成功提示或内存状态写入当作业务完成。demo 继续明确标识并单独覆盖。

数据库使用增量迁移新增草稿和提交记录，历史审核、资产和标注修订不删除、不重写。新增字段和当前客户端兼容性须有 API 契约测试及文档说明。

## 9. 错误与恢复

401 返回重新登录并保留当前页面未保存内容；403 禁止继续写入；404 提示资源不存在或不可访问。409 显示版本、分配或状态变化，停止自动保存并允许重新载入；422 定位具体 Episode／片段及字段。存储、预览或网络失败提供重试，不显示成功。

切换工项、工作空间或 Episode 后，旧请求响应不能覆盖新页面；退出时解除媒体及事件监听。列表刷新不销毁正在编辑的工作台。后台任务失败与业务未通过在页面分别展示，均从后端读取状态。

## 10. 验收与交付顺序

1. 先建立新工项只读工作台投影、不可变提交记录与并发版本门禁，再接编辑器。
2. 完成包内标注、真实草稿保存、刷新恢复、提交及只读结果页。
3. 完成上传后数采审核的连续观看、草稿恢复和一次最终结论。
4. 接通通过版本到资产、候选和 Export 的有效范围，移除涉及入口的假成功行为。
5. 用真实 API 与浏览器完成主链验收，再按另行跟踪的清单整理其余页面。
