## 1. 结论与核查方法

用户对假数据进入正式页面的判断成立。主要问题不是登录后整体切换到了 demo，而是正式页面在真实 API 数据之外，仍混用了演示计算、拼装元数据和仅修改内存的动作。另有新旧业务模型同时存在，造成页面入口、加载器、权限和提交链路不一致。

本次沿「登录与权限 → 采集任务与分配 → 上传后的数据包 → 数采审核及补采 → 建批与治理 → 标注及结果 → 资产 → 数据集导出 → 训练 → 设置」逐项追踪。每项检查页面绑定、数据来源、操作调用、失败处理和后端对应契约；没有因函数名含 mock 就直接判定线上泄漏。

证据等级：

- **正式入口可达**：当前主菜单或其页面按钮绑定到该代码路径；这是代码可达性结论，未声称已在 UAT 点击复现。
- **保留路由可达**：无主菜单，但 `VIEWS`、权限规则和模板仍接受旧 hash。
- **条件可达**：有模板绑定，但取决于接口返回特定字段或状态。
- **遗留代码**：检索未找到正常页面调用入口，应清理，但不计作已确认的正式页面假操作。

优先级：P1 为数据可信度、跨工作空间上下文或业务闭环问题；P2 为流程清晰度、错误呈现与维护问题。这里的 P1/P2 表示严重程度，不对应旧修复计划中的同名阶段。

## 3. 必须先处理的问题

### F01 · P1 · 采集概览把生成值当作业务统计【正式入口可达、函数复现】

证据：`frontend/js/app.js:2153` 的 `miningDash`、`:2110` 附近的种子函数、`:597` 地区列表、`:604` 标签兜底、`:13140` 页面模板。

- 正式模式虽然从真实 `miningTasks` 开始，但趋势、今日新增、有效比例、容量、活跃人数仍在前端生成。日活固定为 12；有效容量／部分趋势固定乘 0.87；人员增幅固定 4.1% 和 7.8%。
- 地区由任务 ID 的种子分配；缺失标签从字典按 ID 取一个。日期范围只改变生成点数和标签，没有按真实事件汇总；默认日标签基准写死为 2026-09-09。
- `loadMiningData` 把包的 `raw/valid` 映射成小时（`:9323` 附近），看板却把它们当 Episode 数再乘估算平均秒数，存在单位错误。
- `loadMiningDashboards` 已调用真实接口，但该页面主体仍绑定上述计算对象，不能仅凭“发了接口请求”认为统计已接通。

另一套 `overview` 首页虽然读取真实看板接口，后端 `backend/data/services/dashboard_warehouse.py:399`、`:495` 仍排除 `data_package_id` 非空的 Episode。这是独立的统计范围缺口：移除前端生成值后，还必须核实新数据包是否计入真实看板，不能只切换接口就宣布统计准确。

复现：抽取源码函数，以 `demoMode=false`、空任务列表求值，得到总任务 0、今日任务 1、今日 Episode 1、日活 12，并仍有活跃趋势。无网络请求、无业务写入。

处理：所有统计回到明确的后端口径；暂未提供的指标显示「暂无统计」，或移除。空数据必须是 0／无数据，不能生成趋势。单位、分母、时间范围和工作空间分别验收；不要用固定比例估算有效数据。

### F02 · P1 · 真实数据详情拼出不存在的文件与固定帧率【正式入口可达、函数复现】

证据：`app.js:1367` `importDetailArtifacts`，`:13542` 固定 `30 Hz`，`:13547` 文件表。列表按钮 `:12140` 可打开该详情。

任意名称都生成 MP4 128 MiB、depth TAR 96 MiB、metadata JSON 18 KiB，未读取真实文件清单。函数复现用 `nonexistent-package` 也得到三条完整记录。

详情还把数据包 ID 放到 Episode 风格的页面中；`loadImportDetailPreview`（`:950`）只挑包内一个可预览 Episode，上一条／下一条切的是外层包列表。用户看到的视频与旁边“文件／Episode 信息”并不构成可靠的一条数据详情。

处理：包详情先展示包内 Episode，选中 Episode 后按其真实元数据、产物、媒体描述符显示。缺失字段显示未知；复用真实 Episode 详情能力，删除假产物函数和固定帧率。

### F03 · P1 · “设为已完成”只改内存【正式入口可达、函数复现】

证据：`app.js:1507` `overviewGovernanceStatus` 优先读 `governanceManualDone`；`:1517` `markGovernanceDone` 设置它并弹成功；`:12134` 模板有按钮。

没有后端状态变更，页面却可以把未完成治理显示为完成。刷新后不再有该状态。

处理：移除该动作。治理完成只读真实阶段结果；若产品以后需要人工豁免，应另设明确的权限、理由、后端记录和状态，不能复用这颗假成功按钮。

### F04 · P1 · “重新检查”未调用真实重试【条件可达、函数复现】

证据：`app.js:1067` `rerunOverviewStage`、`:12140` 异常状态按钮。后端已有 `backend/data/routers/data_batches.py` 的治理重试接口。

函数等待 1.2 秒、改本地覆盖值、刷新采集任务并提示检查完成。没有提交重试任务。当前正式阶段优先取后端报告，所以不能说它一定改变了真实阶段显示；可以确定的是成功提示不代表检查发生。按钮只在模板判为 error 等对应条件时出现，还需要统一业务失败与执行异常的可重试规则。

处理：调用后端重试接口；提交成功只提示「已提交重试」，最终结果跟踪真实任务。失败／超时不能提示检查完成。

### F05 · P1 · 旧云端与切分页面仍能读演示数据【保留路由可达】

证据：`app.js:11` `VIEWS`、`access-policy.js:46` 附近规则、`app.js:7273` 路由处理、`:13079` `miningCloud`、`:13249` `miningCuts`。

- 正式 `loadMiningData` 末尾（`:9366`）仍把 `QuicDataMining.listPipelines/listTransfers` 结果放到页面状态。
- `loadMiningCuts`（`:10366`）无正式模式隔离，读演示切分记录；`retryMiningTransfer`（`:10251`）只操作演示存储。
- `runMiningStage`（`:9821` 附近）走 `simulateBatchStageRun`；云端页面按钮来自这些 action。无主菜单并不等于路由已下线。
- `miningConfig`、`buildData` 也仍在路由集合，但其中一些动作已是真实调用，不能整体描述为 mock。

处理：盘点旧入口的实际替代页后，从生产路由、模板、加载器一起移除／重定向。演示内容只能在独立本地演示入口出现。纯计算工具可以保留，但与演示存储拆开。

### F06 · P2 · 标注进度仍按 ID 计算【条件可达】

证据：`app.js:1088` `annotationItemProgress` 用 `(id + 2) % 3` 等生成标注／通过数量；`:12136` 有真实模板绑定。

仅当行存在 `annotation_status` 或 `annotation` 时启用。当前建批候选序列化未返回这些字段，批次投影又把状态设为空，因此不能声称所有正式行现在都显示假进度；但接口一旦补字段，此路径就会生效。`annotationProgressOf` 也有类似生成逻辑，未找到同等明确的模板调用。

处理：移除生成进度；按冻结 Episode／工项实际数量统计。补接口字段时必须同时排除此路径。

### F07 · P1 · “数据概览／采集数据”实际只展示建批候选【正式入口可达】

证据：`app.js:780` `overviewImportRows` 直接映射 `batchCandidates`；`:1729` 加载候选；`backend/data/services/data_batches.py:74` 只取 `intake_approved` 且未加入任意批次的包。

所以刚上传、待审核、审核不通过、已建批的包都不会出现在这张“采集数据”表。空列表不能解释成没有采集数据；建批后从列表消失是候选语义，不是概览语义。

处理：全部采集数据读取数据包总览；建批选择器单独使用候选接口，或明确把该页命名为「待建批数据」。结合当前截图和导航，优先保留真实总览，在里面进入建批选择。

### F08 · P1 · 包／批次投影缺字段并把未知变成零【正式入口可达】

证据：`app.js:1758` `loadDataBatches`、`:780` 候选投影；`backend/data/routers/data_batches.py:98` `_package_item`。

- 批次成员只从 ID 生成 `package-123`，项目、任务、人员、模态为空，帧数／时长直接设 0；批次接口已有 `valid_duration_hours`，这里也没有用于成员或汇总展示。
- 候选接口主要返回关联 ID，前端却期待 `project_name/task_name/collector_name/device` 等展示字段，导致多项筛选和列无法可靠工作。
- 每个批次加载一份治理报告（N+1 请求）；报告失败被吞掉，落成 queued 或默认 `0/180`，将“没取到报告”混同“任务在排队”。

处理：明确列表展示投影，优先由批量接口返回名称、真实统计与阶段摘要。详细报告按需加载；请求失败展示错误／上次更新时间；未知不是 0，也不是 queued。

### F09 · P1 · 切换工作空间后新页面状态没有完整重载／隔离【正式代码路径】

证据：`app.js:6831` `ensureActiveViewData` 仅随 `activeView` 变化或初始化执行；`:7207` `switchWorkspace` 调旧的 `loadAuthorizedConsoleData`；`:6139` `loadBatches` 仅清理已退役旧状态。

停留在 `intake` 切换工作空间时，切换函数未加载新空间的 `batchCandidates/builtImportBatches`；停留 `batches` 时未加载 `reviewPackageRows`。这些新状态也未在 `loadTaskSets` 中清空，可能继续显示上个空间内容。新包级标注／审核、候选、报告等加载器没有旧 Episode 加载器那样的请求代次校验，迟到响应还能覆盖新上下文。

这是前端上下文问题，不据此断言绕过了后端授权。影响包括错看列表、旧 ID 配合新 workspace 发请求，以及错误后保留旧内容。

处理：以 workspace＋页面／工作项为请求键；切换先清状态与选择，再加载当前模型；丢弃过期响应。用两个隔离工作空间验证快速切换、慢响应、失败和重新登录。

### F10 · P1 · 新标注／审核队列没有连接新工作台【正式入口可达】

证据：`app.js:1844`、`:1859` 新列表；`:1993` 提交函数；`:13417` 新队列表格仅有提交、通过、退回、改派；`:13484` 的“打开工作台”在另一套旧队列模板中。

真实 API 已接，但用户无法从新包级工项完成“打开所有冻结 Episode → 标有效范围并写描述 → 查看提交结果”的连续流程。直接在列表提交或通过不应代替查看和制作内容。

处理：按已认可的工作台设计完成新投影、媒体、草稿版本、逐 Episode 编辑及固定提交结果。统一名称为「标注」和「标注结果」；保留通过／退回，不再额外拆出切分业务。旧工作台能力可复用，旧工作项 ID 不能直接冒充新工项 ID。

### F11 · P1 · 数采审核标记未持久化【正式入口可达】

证据：`app.js:10620` `openIntakeReview` 重置 `rejectedEpisodeIds`，`:10671` 附近切换标记只改数组，`:10693` 最终审核才请求 API。

终审本身是真实请求；但检查多条 Episode 的中间进度不能恢复，刷新／退出后重做，逐条不合格原因也不在当前这个交互中保存。

处理：按工作台设计保存检查草稿与原因；最终审核仍一次，草稿不是多次终审。审核在上传后进行，补采创建关联新包，不修改原包已固定的审核事实。

### F12 · P1 · 新数据集导出缺少异步结果闭环【正式入口可达】

证据：`app.js:1913` 只保存 POST 返回值到 `catalogExportByVersion`；`:1922` 登记按钮用这个内存对象检查 OSS URI；`:13338` 版本操作；后端 `catalog_datasets.py:379` 已有查询导出记录接口。

首次导出是异步 queued：前端显示“已排队”本身正确，但没有对应的查询／订阅完成链路，也不恢复导出记录。Worker 后来成功不自动更新登记能力；页面刷新后内存又丢失。不能把旧 dataset export 的订阅代码当成新 Catalog 的验收证据。

处理：以 export ID 跟踪排队、运行、失败、成功；重新进入按持久记录恢复。显示可用导出格式、有效下载／稳定 URI、失败原因和真实重试。训练登记基于服务端成功记录，不要求用户重复点导出刷新状态。

## 4. 结构、权限与交互问题

### F13 · P2 · 新旧资产／数据集页面和加载器混在一起

证据：`app.js:7333` `navigate`、`:6831` `ensureActiveViewData`、`:7185` 全局加载；`:12880` 新资产表使用 `dataAssets`，`:13314` 新数据集表使用 `catalogDatasets`。

进入新资产页仍会加载旧 Episode 资产；进入新数据集仍加载旧 QRDF dataset/catalog 列表。一些请求共用 loading 标记，增加无关错误、竞态和排查负担。旧 `buildData` 模板以及多套构建／版本 drawer 仍留在主文件。

处理：每个正式页面只加载当前业务模型；旧兼容入口明确重定向或隔离。按页面域拆出模块，不先做无关框架迁移。

### F14 · P1 · 页面权限仍沿用旧接口规则

证据：`access-policy.js` 把资产页按 `episode:read` 放行，新 `backend/data/routers/data_assets.py` 要求 `dataset:read`；训练所有页面按 `train:read` 放行，而 `backend/train/auth_bridge.py:24` 明确仅 `train:read` 不足以使用当前训练桥接。

新队列操作按钮主要按队列种类决定，缺少对应状态和可执行动作判断；资产构建、数据集导出等按钮也不能只沿用页面读权限。这些不等于后端越权成功，但会让用户见到无法执行或不该出现的入口。

处理：逐接口统一视图读权限、操作写权限、任务归属和当前状态。优先使用服务端可执行动作；分别用管理员、运维、数采员／标注员／审核员和只读角色做验收。保留后端鉴权，不用隐藏按钮代替安全边界。

### F15 · P2 · 字典缺失／失败被替换为“默认真实数据”

证据：`app.js:9275` 附近正式 `dictMap` 固定软件版本、默认项目、用途和场景；`:9304` 附近任务展示默认归到「默认采集项目／正式任务」；`:6424` 设置加载把失败 catch 成空列表。

静态业务枚举可以存在，但项目、标签、软件版本事实不能用示例值补齐。设置页读失败呈空列表，用户容易误以为数据未创建；任务关联丢失也被默认名称掩盖。

处理：枚举、输入默认值、服务端字典、业务事实分开；缺失映射显示「未关联／未知」，读取失败提供重试。配置中心作为正式维护入口，旧 `miningConfig` 路由另行退役。

### F16 · P1 · 离线任务清单请求失败仍下载并提示成功

证据：`app.js:10824` 起的 `downloadTaskOfflineManifest`，包列表请求失败只 `console.warn`；CSV 用兜底一行，JSON 输出空 `packages`；`:10907` 附近统一成功提示。

离线清单会影响实际数采执行，不能把“请求失败”当成“确实没有包”。导出列仍显示「责任人ID／操作人ID」，也和用户确认的一包一数采员界面概念不一致。

处理：取数失败停止下载并明确报错；真实空清单明确说明；优先复用服务端正式 manifest 契约。展示按「分配数采员／实际采集人员」解释已有字段，不新增负责人流程。未来在线下发复用同一任务／包事实。

### F17 · P2 · 上传完成时间被 updated_at／计划时间代替

证据：`app.js:873` `matchOverviewFilters` 按 `updated_at` 筛「上传完成时间」，还把 datetime 截成天；`:12086`、`:12139` 显示同字段；`:11571` `miningBatchUploadEndText` 优先用 updated_at，还可从计划 window 推算年份／日期。

审核、分配等更新都可能改变 updated_at，它不等于上传时间；当天时分秒筛选也没有兑现。数采审核列表已有真实 `upload_completed_at`，可以统一。

处理：显示和筛选同一真实时间字段；未知显示空，不从计划时间猜测。日期范围明确时区和边界。

### F18 · P2 · 训练向导失败可继续提交，项目范围不明确

证据：`frontend/js/train-console.js:279` 固定 `project_id`；`:289` `nextStep` 即使校验失败仍进确认页；`:121` 附近提交按钮仅 loading，未按校验阻断；`:305` `submitJob` 不检查校验结果。

后端依旧可能拒绝非法任务，本项不声称能绕过服务端。用户看到阻断提示后仍能继续发送请求；修改参数后也需要重新校验。

固定 `prj_robot_arm` 与当前后端默认项目一致（`backend/train/src/quictrain_api/settings.py:56`、`schemas.py:14`），**不能据此把训练判为 mock**。但页面没有说明这是训练平台的默认项目，也未定义与 Studio 工作空间的关系。

处理：阻断失败／未完成／已失效的校验；提交前使用当前参数校验。明确当前单训练项目范围，若以后支持多项目再提供真实选择，不在本期顺带重构训练平台。

## 6. 页面应如何收敛

建议正式路径保持：**数采任务 → 分配数采员 → 上传后的数据包 → 数采审核 → 整包建批 → 治理 → 标注 → 标注结果与通过／退回 → 资产 → 数据集版本 → 导出／训练登记**。

- 采集概览只展示有真实口径的统计。没有后端统计的卡片先撤掉，不靠更好看的假曲线占位。
- 采集任务负责计划、拆包、分配和补采关联；采集资源负责数采员及设备。一个包当前只进一个批次，未来包多次建批单独扩展，不增加本期流程。
- 数采审核处理上传后入库准入；数据概览统一看包，不再把建批候选冒充全部数据。页面标题「数据接入／采集数据包」与菜单「数据概览／数采审核」也要一致。
- 标注包含片段选择和语言描述；结果页直接展示内容，只保留必要的通过／退回。移除独立旧切分导航、旧模式切换和重复审核标题。
- 资产展示名称、来源任务／包、有效时长和可查看的固定结果，不只放 batch/workspace 数字 ID、技术状态字符串。
- 数据集页显示持久版本与导出状态。LeRobot 入口提供真实来源选择或明确可执行的导入路径，不要求普通用户猜 `native_lerobot_dataset_id`。
- 训练数据集是 Studio 导出结果在训练平台的登记视图，需要说明来源及回链，避免看起来像又造了一份数据。七个训练菜单是否合并可以后续按使用频率定，不因页面多就把真实功能删除。
- 将旧路由、孤立 drawer、旧数据加载器和只对演示有效的按钮一起清理。只删菜单不足以完成下线。

### 9.3 拆分边界

沿用现有 Vue 与同源静态部署，先使用页面组件和浏览器模块／受控按需加载，不把引入新框架或构建系统设为本期前提。若后续剖析证明运行时模板编译或全量组件库仍是主要瓶颈，再单独评估预编译和构建改造。

以下是目标职责，不要求一次创建所有目录；每修一个业务域就迁移对应代码，避免建立一套新代码后旧代码仍长期运行。

| 模块边界 | 负责内容 |
| --- | --- |
| `app` / shell / router | 应用启动、身份、导航、路由装载、页面错误边界；不保存各页面所有表单和列表 |
| `api` / request / scope | 请求、鉴权、错误规范、取消／去重、范围请求键；具体领域 API 可分文件，不能反向依赖页面 |
| `i18n` / shared | 文案、日期、格式化和真正跨页面组件；不变成另一个巨型 utils |
| collection | 任务、拆包、分配、数采员与设备、manifest 与补采操作 |
| packages / intake-review | 上传状态、包总览、Episode 目录、数采审核草稿与终审 |
| data-batches / governance | 候选、建批、阶段摘要、治理报告与真实重试 |
| annotation / results | 新工项、工作台、固定提交结果、通过／退回 |
| workbench 内部组件 | Episode 列表、播放器、时间轴、片段编辑、保存协调、撤销与快捷键；视图与纯时间计算分离 |
| assets / datasets | 固定资产、数据集版本、导出记录及状态恢复；共用异步任务跟踪能力 |
| dashboard / train / admin / settings | 独立页面装载与状态；图表仅随 dashboard 装载；训练保留现有组件边界 |
| styles / demo | 基础 token／布局与各域样式分离；演示入口和数据隔离，正式 helper 从演示存储抽出 |

规模约束：模块以单一职责和依赖方向为主要标准。业务 JS 或模板超过约 800 行触发拆分检查，超过 1,500 行需要在评审中说明保留原因；字典、生成代码另行统计。这是维护提醒，不是为了行数把紧密逻辑打散。重点是把当前 14,075 行主文件缩成只负责装配的外壳。

拆分必须同时搬迁模板、样式、状态、接口和对应测试，移除原入口；测试改为导入纯模块或验证真实组件行为，避免继续搜索整个 app.js 字符串。保持可单独回滚的小提交，并核验 hash 深链接、刷新、角色和工作空间切换。

### 9.4 测量与完成标准

先在同一浏览器版本和固定设备上记录基线，再比较改动。分别测试冷缓存、暖缓存、普通网络及受控弱网；记录硬件、浏览器、CPU／网络限制、数据规模和提交 SHA。不得拿不同设备／不同数据量的结果比较。

覆盖场景：登录、首页、切工作空间、100／1,000／10,000 条总记录下的分页列表、100 个批次的治理列表、100／1,000 个 Episode 的包、当前 Episode 100／1,000 个片段、连续打开关闭页面与媒体。压力数据仅放隔离测试环境，不进入正式生产响应。

| 维度 | 验收要求 |
| --- | --- |
| 首屏体积 | 普通登录入口不请求 demo、训练、图表或工作台模块；分别报告业务 JS、vendor、CSS 的原始与实际压缩传输量。以当前 gzip 估算约 1.02 MB 为静态参考，首轮争取减少至少 30%，最终以浏览器网络记录确认 |
| 加载耗时 | 分别记录首屏可操作、页面主体可见、当前视频可播放时间，以及脚本解析／模板编译长任务；至少 10 次同条件运行，报告中位数与最慢值。没有实测前不填“已提速 X%” |
| 请求 | 同一用户／空间／参数的并发 GET 最多一份；切页不加载未访问业务域；100 个批次首屏不发 100 次完整报告请求；导出跟踪同 export ID 只有一个订阅／轮询器 |
| 列表 | 总记录从 1,000 增到 10,000 时首屏响应条数与 DOM 规模仍受页大小／窗口约束；筛选排序在服务端执行，不能取全量后只展示第一页 |
| 交互 | 本地片段选取、输入和拖动以 200 ms 内反馈作为本期目标；标明测试设备及场景。剖析超过 50 ms 的主线程任务，区分前端计算与接口／视频等待，不用 loading 动画替代交互完成 |
| 内存与清理 | 预热后连续切页／开关媒体 30 次，检查堆、DOM、图表实例和事件订阅数量是否回到稳定区间；允许有上限缓存，不接受随次数持续增长。不可仅凭调用 dispose 就认定通过 |
| 正确性 | 分页不丢选择、过期请求不串空间、缓存不跨用户、提交不丢草稿、撤销有效、通过版本固定；性能优化不得删掉现有保护或使用假统计代替真实结果 |

本节完成的是体积测量、源码定位及整改约束；浏览器 CPU／网络／内存基线和以上目标均待实现阶段验证。性能测试和功能测试同时作为每批交付条件，不因文件已拆小就勾选“性能优化完成”。
