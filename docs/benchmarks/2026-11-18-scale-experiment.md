# 可复现规模实验 · 2026-11-18（10 万 / 100 万行）

## 范围

测量 `robodata.quality.run_checks(episode, check_video=False)` 对固定宽度 Episode 表格的**表格质检路径吞吐**。每行含 6 维 `observation.state`、6 维 `action`，并执行必需字段、行数、身份、形状、有限数值、帧索引与时间戳检查。

**不包括** fixture 构造、Parquet 读取、文件指纹、视频解码、LeRobot 转换、压缩打包、并发请求或服务开销。因此这不是端到端处理性能，也不能外推成生产容量或相对旧版本的提速。

## 可复现命令

```powershell
uv run --locked python scripts\benchmark_quality.py `
  --rows 1000,5000,10000,100000,1000000 `
  --repeats 3,3,3,3,1 `
  --output docs\benchmarks\quality-table-2026-11-18.json
```

前四档重复 3 次，100 万行档只跑 1 次（单次约 1 分钟，避免把实验拖成 3 分钟）。脚本固定使用零向量状态、单位向量动作与 30 FPS 等间隔时间戳；数据构造在计时区外。运行环境与全部原始字段见 [JSON 结果](quality-table-2026-11-18.json)。

## 怎么读这张表

- **1 万行以内**：吞吐约 8 万行/秒，三档处于同一数量级，说明表格检查本身没有明显的固定开销。
- **10 万行**：中位数掉到约 2.1 万行/秒，但三次中最好一次仍是 1.21 秒（约 8.3 万行/秒）。波动来自对象数组的内存分配与垃圾回收，不是稳定算法退化。样本只有 3 次，不能据此拟合复杂度曲线。
- **100 万行**：单次 61.25 秒、约 1.63 万行/秒。它证明当前实现能在单机内存中处理 100 万行表格并给出 0 个数据问题，**不证明**端到端转换、视频解码或并发服务能承受同等规模。

每行结果中的 `incomplete` 是预期状态：实验显式关闭视频检查，所以总体质检不应伪装成完整通过；表格检查没有数据问题。

## 边界

- 合成数据只有 6 维状态/动作，真实数据集的行宽、字符串列、嵌套字段和视频会改变耗时。
- 100 万行档只跑 1 次；100,000 行档方差很大，应比较分布而不是单个数字。
- 没有并发、磁盘 IO、Parquet 读写、视频解码、LeRobot 转换和打包。
- 没有修改前后对比，因此**不声称性能优化**；这里只建立当前路径的可复现基线。
- 如果要估计完整链路容量，下一阶段需分别计时 Parquet 读取、表格检查、逐路视频解码、转换和打包，并记录内存峰值与失败行为。
