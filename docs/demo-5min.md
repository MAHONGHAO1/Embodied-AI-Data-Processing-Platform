# 具身数据平台 · 5 分钟面试讲解稿

目标：用 3–5 分钟讲清**问题、工程决策、可核对证据与边界**。默认控制在 4 分钟；如果面试官追问，再从最后的证据索引展开。

## 演示前准备

- 本地启动具身工作台，打开 `http://127.0.0.1:8765`；确认可进入已准备好的 ALOHA Coffee 验收批次。启动方法见 [README 安装与启动](../README.md#安装与启动) 与[八分钟路线](demo.md)。
- 同时准备以下只读证据： [v0.6 验收记录](VALIDATION_v0.6.0.md)、[v0.8.0 发布说明](../RELEASE_NOTES_v0.8.0.md)、[线上静态作品集](https://mahonghao1.github.io/Embodied-AI-Data-Processing-Platform/)。
- 若本机没有 ALOHA 批次，只展示线上静态页面与已提交验收记录；不要把 UI 布局验证图说成实际业务状态。

## 逐分钟话术与操作

### 0:00–0:40 · 问题与定位

**话术：**

> 我做的是一条本地机器人演示数据工作流，解决的不是“把文件转个格式”这么简单，而是让来源、逐路检查、转换结果和最终交付包能互相核对。项目里 Python 负责数据与业务逻辑，React/TypeScript 负责浏览和证据呈现，FastAPI 只在本机提供接口。

**操作：**打开批次总览，指出服务地址是 `127.0.0.1`；说明这是本机应用，GitHub Pages 只是静态作品集。

### 0:40–1:25 · 固定来源与范围

**话术：**

> 我把 ALOHA Coffee 的来源 revision 和文件清单固定下来。本次真实验收只覆盖 Episode 0–4，共 5 条、5,500 帧、四路相机。原始来源只读；处理过程保留可追溯输入与运行证据。

**操作：**打开批次来源信息或数据概览，展示 revision、许可、任务数和帧数。不要把公开数据集的全量规模说成本机验收范围。

### 1:25–2:20 · 多相机检查与时间轴

**话术：**

> 每路相机分别检查文件是否存在、能否解码、帧数和样本时间映射。我在 v0.8.0 把视频、状态曲线和动作曲线放到同一条时间轴上；书签跳转会更新真实视频的播放时间和曲线游标。这个映射检查不等于相机硬件同步，也不证明控制因果关系。

**操作：**打开 Episode 浏览器，先展示逐路检查结果，再点一个底部百分比书签，观察视频时间与曲线游标一起移动。只在实际加载了真实四相机批次时才现场展示四路画面。

### 2:20–3:10 · 质检、转换与失败门禁

**话术：**

> 质检覆盖字段、任务长度、向量维度、有限数值、帧索引、时间戳和视频映射。随后由官方 LeRobot 库写入目标格式并离线加载验证。运行记录保留阶段状态与诊断；失败的运行不会登记成可交付结果。

> 自动验收里的标注审核门禁是脚本模拟，用来测试流程门禁，不代表人工审核。

**操作：**打开质检报告或运行诊断，展示规则覆盖、问题记录和运行阶段；避免只展示“通过”徽标，要能打开具体证据。

### 3:10–4:00 · 交付验包与结论

**话术：**

> 最后不是只看转换命令退出码。我检查输出质检、官方离线加载、交付 ZIP 的清单与哈希，并独立解包复核。本次固定样例的 55/55 项输出质检通过，5,500 帧数值核对与独立验包通过。这个结果证明的是固定样例的数据读取、检查、转换和交付，不证明模型训练效果、机器人成功率或通用数据集兼容。

**操作：**打开交付核验与验收记录，展示报告、清单和独立验包结果；最后停在能力边界页。

## 讲解纪律

- 只说当前屏幕或文档能直接证明的事；样例规模、构造 UI 数据和模拟审核分别说清。
- 如果应用没启动或没有本地 ALOHA 批次，切到静态作品集并标明它不能执行交互；不要现场假装数据来自当前服务。
- 面试官需要深入时，按“来源 → 规则 → 运行记录 → 交付包”展开，而不是继续堆技术名词。
