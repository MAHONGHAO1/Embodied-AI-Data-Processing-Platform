# 数据契约（随包走的验收结论）

质检跑完得到一份报告。报告留在本机，对下游没有意义——包一旦交出去，对方没法读你的工作目录。
所以报告里要紧的那部分，要跟着包一起走。这份文档定义那部分长什么样。

叫它契约，是因为它同时约束两件事：交出包的人要如实写清楚查了什么、没查什么；拿到包的人不用重新跑一遍，就能判断这份数据能不能用。

---

## 文件

一个交付包旁边放两个文件：

| 文件 | 给谁看 | 内容 |
|---|---|---|
| `QUALITY_REPORT.json` | 程序 | 报告的稳定子集，见下面字段表 |
| `QUALITY_REPORT.md` | 人 | 同一份结论的可读版本，一页以内 |

放在交付 ZIP 的同级目录，或者直接放进 ZIP 里。两种都可以，但要固定一种，不要每次不一样。

## 字段

`QUALITY_REPORT.json` 取自质检报告，只留这些字段：

```
schema_version          报告结构版本
app_version             工作台版本
rule_version            判据版本，见 docs/RULES.md
params                  实际使用的阈值
check_video             这次跑没跑视频检查
input_fingerprint       输入文件指纹
result_digest           结论摘要
source.source_kind      数据来源类型
source.manifest         来源清单
source.integrity_status 完整性比对结果
summary                 各类计数
limitations             明确不判的项
issues                  逐条问题
```

`episodes` 数组和 `runtime_seconds`、`started_at_utc` 可以留着，但契约的最低要求是上面这些。少了任何一项，这份文件不构成契约，只是一份日志。

## 结论口径

收到包的人只关心一个问题：这包能不能用。三个答案，写死在 `summary` 里：

| 结论 | 判定条件 |
|---|---|
| **可交付** | `data_issue_count = 0` 且 `load_failure_count = 0` 且 `not_checked_count = 0` |
| **不通过** | `data_issue_count > 0` 或 `load_failure_count > 0` |
| **结论不完整** | 前两条都不是，但 `not_checked_count > 0` |

第三种最常被漏掉。跳过视频检查、来源没给 fps、某一路相机没查完，都会进这一类。它不是"通过"——是**这次没查全，别当通过用**。

`QUALITY_REPORT.md` 的第一行就写这三者之一，不要写"整体良好"之类的话。

## 未检查项必须写出来

`limitations` 原样复制，一个字不删。它写的是判据不覆盖的东西：

- 只检查记录与文件内视频的时间对应，不代表硬件同步或双相机同步。
- 不判断动作的控制含义、物理安全性、任务成功率或训练适用性。
- 完整性比对只针对本地下载清单，没有重新做在线来源校验。

另外，`not_checked` 类的 issue 逐条保留。每一项都是一句"这项我没查"，它们让下游知道边界在哪，而不是靠猜。

## 校验

`result_digest` 是报告去掉时间与运行信息后按固定顺序序列化、再取 SHA-256 的结果。收到包的人可以对 `QUALITY_REPORT.json` 重算一次，确认结论没被改过。

它证明的是"结论没被篡改"，不证明"结论是对的"。判据本身错没错，看 `docs/RULES.md` 和 `fixtures/known-bad/`。

## 边界

契约随包走，但它不自动生效。不写它，交付照样成立——只是下游要自己想办法验。所以它是一件约定，不是一道强制关卡：愿意用它的人拿到更好的信息，不愿意用的人不受影响。

这条边界要说在前面，免得被当成已经有人在用的行业标准。
